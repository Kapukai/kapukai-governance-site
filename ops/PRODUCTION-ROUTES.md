# Public route ownership and release checks
Run `python3 ops/check-production-routes.py` from a checkout. No account, API token, service credentials or form submissions are used. Print `--inventory` to compare tracked HTML and the legacy release manifest with the monitored routes. The portfolio catalog and share-card manifest serve other purposes and are not proof that this project publishes every URL they mention.

The jobs check success after production deployment_status events, on manual workflow dispatch, and daily if a deployment integration didn't emit an event. A failed check appears in GitHub Actions. This workflow sends no email or Slack notices and changes neither host. Compare with the existing exception queue rather than creating duplicate operator alerts.

Only `ops/production-routes.json` managed entries and discovered monthly archive pages are eligible to be compared against repository source and the mirror. `observe_only` checks additional deployed pages without authorizing sync. `outside_this_mirror` records known routes with different publishers. Register a new owner and verify its paths independently before broadening the mirror.

The checker compares headings, text, navigation, form fields, CTA destinations and page metadata from the final HTTP response with source HTML, and checks referenced CSS, scripts, local images, favicons and preview images against the source bytes. Same-path trailing-slash normalization is accepted; redirects to a different host or path fail. A branded mirror may use only content-addressed aliases for shared community CSS and JS, where both path digest and served contents match the source. Asset fetches are restricted to the configured public hosts. Third-party link availability, JavaScript execution, CMS/API routes outside the registry, actual form submission, inbox delivery and operating-system notification preferences are outside this check.
